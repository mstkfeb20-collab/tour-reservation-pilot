# 命名・作法

管理者は案件リーダー。ここに書いたルールのうち、機械的に判定できるものは順次 `scripts/lint/domain/` に移す。

> 以下は見本です。案件の技術スタックに合わせて書き換えてください。

## 命名
- クラス名・メソッド名は `docs/domain/glossary.md` の「コード上の名前」に合わせる。
- テストクラスは `<対象クラス>Test`、`@DisplayName` は日本語で業務の言葉を使う。

## 作法
- 値は不変（final フィールド、セッターなし）を基本にする。
- 状態の変更は意味のある名前のメソッドで行う（`setStatus` ではなく `cancel()`）。
- 例外メッセージは日本語で、何が起きたか・なぜできないかを書く。
- コメントで「なぜこう書いたか」を説明したくなったら、まず名前と構造で表せないか考える。回避策をコメント付きで残すと、エージェントがそれを手本として広げる。

## 上書きのルール
- 組織の標準 → 案件の標準 → タスク固有 の順に優先する。
- 業務の不変条件とセキュリティは上書きできない。
- 命名・作法は、理由をこのファイルに書けば上書きできる。

## 設計から転記した決まり（S-13-001 メッセージ・ログ設計書：メッセージ・ログ設計書）

## 設計から転記した決まり（S-32-001 運用設計書：運用設計書）

- 画面のエラー率が5分間で1%を超えたら通知する（S-32-001-003・運用監視項目）
- 問い合わせは相関IDで画面・API・バッチのログを追う（S-32-001-004・障害時の切り分け）
- 取込結果テーブルと不一致リストを、勘定日と照会番号で突き合わせる（S-32-001-005・障害時の切り分け）
- 月初に、保持期間を過ぎた一時ファイルを削除する（S-32-001-006・定期メンテナンス）
- DB を変えるリリースには、戻すためのスクリプトを用意する（S-32-001-007・リリースと切り戻し）
- J110 の新しい版は、前日分のファイルで旧版と結果が一致することを確かめてから切り替える（S-32-001-008・リリースと切り戻し）
- 取消料率表などの設定変更も、コードと同じくレビューを通す（S-32-001-009・設定変更の手順）
- 改修の影響範囲は himotoki で要求から候補を出して確かめる（S-32-001-013・保守時の影響調査）

## 設計から転記した決まり（S-34-001 開発ガイド：開発ガイド）

- エージェントには本番DBへの接続・強制 push・reset --hard をさせない（S-34-001-001・実行させない操作）
- 要件・不変条件・base スキル・共通 Lint はエージェントに編集させない（S-34-001-002・編集させないファイル）
- --no-verify や Lint の無効化でチェックを飛ばさせない（S-34-001-003・チェックの回避の禁止）
- ソースや予約データを、許可されていない外部サービスに送らせない（S-34-001-004・外部への送信の禁止）
- Lint・テスト・完了条件のテストがすべて通ったら完了とする（S-34-001-005・完了の定義）
- PR には実行したコマンドと結果を添える（S-34-001-006・PRに添える証拠）
- 設計に書かれていないことは推測で埋めず、質問として PR に書く（S-34-001-008・迷ったときの扱い）
- 旧システムの設計書からの業務ルールは base-spec-extraction で候補にし、予約担当の承認を得る（S-34-001-009・業務ルールの抽出元）
