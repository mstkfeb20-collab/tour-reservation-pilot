# 品質の考え方

tazuna を使うウォーターフォールの開発で、**何を品質管理の対象にし、何を見て、何を測り、何を判断するか**をまとめる。品質計画を書くときの拠り所にする。記録は [`metrics.md`](metrics.md)。

## 何が変わるか

従来の品質管理は、人が作った成果物を人が検査する。設計書をレビューして指摘密度を見て、コードを書いて試験してバグ密度・試験密度を見る。

AI がコードとテストを書くと、この前提が二つ崩れる。

- **コードを書く速さは差にならない。** 差になるのは業務知識・設計品質・レビュー品質。AI は書かれていない業務ルールをもっともらしく補うので、設計で決めていないことは、どれだけ速く書いても正しくならない。
- **AI の成果物を人が全部検査するのは現実的でない。** AI はテストが通るまで自分で直してから出すので、単体テストのバグ密度は構造的に 0 件になり、指標として成り立たない。テストの件数もいくらでも増やせる。

そこで、品質管理の対象を次のように移す。

> **成果物を検査する**から、**品質を作る仕組み（設計とゲート）を管理し、成果物は機械のゲートと独立した試験で確かめる**へ。

| 工程 | 品質を作る・確かめるもの | 人がすること | 主な指標 |
| --- | --- | --- | --- |
| ① 設計（ID 設計書） | 人の設計とレビュー | 設計する・レビューする | 人のレビュー指摘密度 |
| ② 転記 | 転記ツール（機械）＋人の確認 | 機能の横断面を確かめる | ①に合算（見つかった場所を分ける） |
| ③ 実装・単体テスト | ゲート（`mvn verify`・Lint・CI） | ゲートの基準を決める。コードはレビューしない | 消化率・分岐カバレッジ・ミューテーション・セキュリティ |
| ④ CI | ③のゲートを PR ごとに動かす | — | ③に含める |
| ⑤ 結合・総合テスト | 独立した試験（ED・SP から） | 試験を起こし、実行する | 試験密度・バグ密度・原因区分・引き渡しの消化率 |

二つのことを分けて見る。混ぜると、案件の出来と型の出来の区別がつかなくなる。

- **案件の品質**: この案件の成果物の品質。従来の品質報告に載せる。
- **型の品質**: tazuna（ハーネス・転記ツール・ゲート）が効いているか。`rule-log.md` に記録し、月次で標準化チームに返す。

## 指標の規模（分母）

従来の基準値を捨てず、**比率で換算して使う**。

- **設計書**: Markdown には枚数がないので、**決定の行数**（`- [n] 本文` の行。廃止の行を除く。見出し・空行・図の行は数えない）を分母にする。従来の枚数あたりの基準値は、「1枚あたりの決定の行数」で割って行数あたりに換算する（例: 0.010〜0.016 件/枚、1枚 20 行なら 0.0005〜0.0008 件/行）。値が小さすぎるときは「100行あたり」などの単位にする。1枚あたりの行数と単位は、パイロットで従来の設計書と同じ範囲を書いた実物から決める。
- **コード（KLOC）**: AI は同じ機能でも人より多く書くことがあり、KLOC が膨らむと密度が見かけ上下がる。**過去の類似案件（人が書いたもの）と比べた比率**で基準値を換算する（例: 人が 100K の範囲を AI が 200K で書いたなら、KLOC あたりの基準値を半分にする）。範囲の違いが混ざらないよう、画面数・バッチ数・機能数など類似案件とそろえやすい単位あたりの KLOC で比べる。モデルやハーネスを大きく変えたら比率を測り直す。
- **集計の単位**: PR ごとに記録し、判定は機能群か工程全体でまとめて行う。件数が少ないと偶然の揺れが大きい（10 件なら ±3 件程度は偶然でも動く）。PR ごとの値は、異常を見つける目印にだけ使う（大きい PR なのに指摘 0 件など）。

## ① 設計（ID 設計書）

AI は設計の曖昧さを吸収しない。従来は実装者（協力会社）が問い合わせや暗黙の了解で補っていたものを、AI はもっともらしい推測で埋める。**「人が読めば分かる」設計は、AI にとっては欠陥**になる。品質を作るコストは、この工程に寄る。

**見るもの**

- 業務として正しいか（業務ルール・例外・境界値）。人にしか判断できない
- 解釈が一通りに定まるか、項目に抜けがないか、書類どうしが噛み合っているか（点検で先につぶす）

**点検とレビューを分ける**

- **点検**（スキル `base-design-review`）は、書き手が人のレビューの前に使う道具。**レビューではない**。形式・食い違い・未定義・抜け・書式の解釈・テストの置き場所を、根拠の行IDつきで出す。件数は品質の指標にしない（コンパイラの警告をつぶした件数を、コードレビューの指摘に数えないのと同じ）。
- 点検が済んでいることが、**人のレビューを始める条件**。結果を `docs/review/設計書の点検.tsv` に残し、止める種別（食い違い・未定義・場合分けの抜け・書式の解釈）は直すか「残す: 理由」、質問は issue にする。設計書を変えた PR では Lint（COMMON-011）が確かめる。
- **人のレビュー**は、業務として正しいかに集中する。

**決まっていないこと**

- 点検の質問は、業務で決めること。**issue にして追う**（スキルが下書きを出し、書き手が作る）。
- 必須の見出しに「該当なし（理由）」と書くのは「書くことはない」という**決定**。何も書いていない必須の見出しは**未決**。未決は要件ファイルの「未決」に転記され、エージェントは実装もテストもしない（PR に「未対応: 行ID（未決）」）。決まったら、その issue で設計書を直す。

**測るもの**: **人のレビュー指摘密度**だけ。レビューのコメントの先頭に分類を書き、先頭で数える。

| 分類 | 当てはまるもの | 品質の判定 |
| --- | --- | --- |
| `[誤り]` | 業務として、または書類どうしで正しくない | 入れる |
| `[欠落]` | 書くべきことが書かれていない | 入れる |
| `[表現]` | 意味は合っているが、読み違える書き方 | 入れる |
| `[課題]` | 業務で決めることが出てきた（設計者のミスではない）。issue にする | 入れない（件数は別に報告する） |

- 決める必要が出た指摘も、レビューで出た時点で1件と数え、分類を `[課題]` にして品質の判定から外す。
- 課題が決まって設計書を直す PR も設計レビュー。そこで出た指摘は数える。決まったこと自体は数えない。
- 再レビュー（直したことの確認）は数えない。再レビューで新しく出た指摘は数える。

**判断すること**

- **出口基準**: Lint が通る（COMMON-007・011）。止める種別の点検結果が残っていない（または理由付きで残す）。質問がすべて issue になっている。業務の担当者が承認している。
- **品質の評価**: 指摘密度を従来と同じように読む。上回れば設計の品質が低く、下回ればレビュー不足の疑い。
- **基準値はパイロットで作り直す**。過去の基準値は「人だけでレビューした」前提。点検で形式・噛み合いの問題が先につぶれるので、人の指摘は下がるはず。それまでは推移で見る。

## ② 転記

転記はツールが機械的に行い、転記先は手で直さない（Lint COMMON-008）。だから転記の PR での指摘は、必ず「設計書を直す」か「転記ツールを直す」のどちらかになる。

- **位置づけ**: 設計工程の**最後の検査**。機能の横断面（完了条件・テスト仕様）を、人が初めてまとめて見る場面で、書類ごとのレビューでは見えなかった誤り・欠落が見つかる。
- **見るもの**: 機能の完了条件とテスト仕様の過不足。未決が運ばれているか。行の移り先が正しいか。
- **測るもの**: 設計起因の指摘は**設計工程の指摘として合算**し、「転記の PR で見つかった」と分けて記録する。転記の PR での指摘が多ければ、書類ごとのレビューで書類をまたぐ観点が抜けている。転記ツール起因は型の品質（rule-log）。
- **判断すること**: Lint が通り、未決の件数が見えていて、人が承認したらマージ。設計起因が見つかったら設計の PR に戻して直し、転記し直す。

## ③ 実装・単体テスト（④ CI を含む）

**人はコードをレビューしない。ゲートを通ればマージしてよい。** そのぶん、品質管理の対象は**ゲートそのもの**になる。ゲートが甘ければ品質も甘くなるので、ゲートの強さを数字で示す。

**見るもの（ゲートの中身）**

- 設計からのテスト: テスト仕様の行がすべてテストになっているか（行IDの `@Tag`）
- 一般的な観点のテスト: 正常系・準正常系・異常系・境界値・禁止事項（スキル `base-test-design`）
- テストの強さ: 形だけのテスト（アサーションが弱い）を機械で見つける
- セキュリティ: 静的解析

**テストの置き場所（単体と結合の振り分け）**

- **単体**: 1つの機能の中で、DB・他の機能・外部を置き換えて確かめられるもの（業務ロジック・入力の検査・状態の移り方など）
- **結合**: 実際の DB の振る舞い（ロック・トランザクション・途中で止めての再実行）、機能をまたぐもの（同時実行・回帰）、外部とのやり取り（実際の受信・送信）
- 結合のものを単体に書くと、AI はモックで置き換えて「通る」テストを作り、消化率は 100% なのに何も確かめていない状態になる。テスト仕様書の「結合・総合テストの観点」「回帰テストの範囲」に書き、単体の PR では「未対応: 行ID（結合テストへ引き渡し）」とする。点検の観点「テストの置き場所」が見つける。

**ゲートを抜け道にしない**

- モックにしてよいのはポート（interface）だけ（Lint COMMON-012）。業務ロジックをモックにしない。
- 設計由来のテストの期待値を、実装に合わせて書き換えない。設計を変えずに書き換えた PR は、PR レポートが知らせる。
- テストを消したり止めたりして通さない（hooks・Lint）。基準値・対象・除外を変えて通さない（変えるのは品質計画を決める人）。

**測るもの**

| 指標 | 見るもの | 取り方 |
| --- | --- | --- |
| テスト仕様の消化率 | 設計で決めた観点がすべてテストになったか（従来の試験密度の代わり。件数では見ない） | PR レポート |
| 分岐カバレッジ | テストが通っていない分岐がないか | JaCoCo（`mvn verify`） |
| ミューテーションスコア | テストが本当にバグを検出できるか（わざと壊したコードを検出した割合） | PIT（`mvn verify`） |
| セキュリティの指摘 | 静的解析で見つかったもの（0 件でマージ） | SpotBugs ＋ FindSecBugs（`mvn verify`） |

- 基準値は品質計画で決め、`pom.xml` の `tazuna.coverage.branch.min`・`tazuna.mutation.min`・`tazuna.mutation.targets` に書く。
- 単体のバグ密度は取らない。
- 依存ライブラリの脆弱性は `mvn verify` では見ない（脆弱性データベースの取得が社内プロキシで重い）。GitHub は Dependabot、GitLab は Dependency Scanning を使う。

**判断すること**

- **マージしてよいか**: ゲートがすべて通る。テスト仕様の消化率 100%（残りは「未対応」で理由がある）。PR の質問がすべて回答済み。
- **単体工程を終えてよいか**: 全要件が実装されている。未対応の行（未決・結合テストへ引き渡し）の一覧を試験チームに渡せる（スキル `base-navigator`）。
- **「ゲートを通ればOK」は宣言ではなく仮説**。⑤ の実装起因の不具合で確かめる。

**残るリスク**: コードとテストを同じ AI が同じ要件から作るので、AI が要件を読み違えると、コードもテストも同じ読み違いをしてゲートを通る。人が決めたテスト仕様（設計のテスト観点）がその歯止めになる。設計そのものの誤りは単体では見つからない（従来の単体テストも同じ）。⑤ で拾う。

## ⑤ 結合・総合テスト

tazuna の範囲外で、試験チームが ED・SP から起こす。作った人とは別の人が、別の根拠から確かめる**唯一の独立した検証**で、① の設計品質と ③ の「ゲートを通ればOK」の両方をここで確かめる。

**見るもの**

- 試験チームが起こしたテストケース（ED・SP 由来）
- tazuna から引き渡された項目: 未対応の行（「結合テストへ引き渡し」「未決」）
- 見つかった不具合と、その原因（不具合の issue の「原因区分」）

**測るもの**

| 指標 | 見るもの | 読み方 |
| --- | --- | --- |
| 試験密度 | 試験の量（テストケース数 ÷ 規模） | 従来どおり。KLOC は類似案件との比率で換算した基準値を使う |
| バグ密度 | 不具合の量（不具合数 ÷ 規模） | 従来どおり |
| 原因区分ごとのバグ密度 | 設計・転記・実装・ハーネスのどこで入ったか | 下の表 |
| 引き渡しの消化率 | tazuna から渡した項目が、結合のテストケースで全部確かめられたか | 100% が完了条件。抜けると単体でも結合でも誰も確かめていない穴になる |

| 原因区分 | 意味 | 返す先 |
| --- | --- | --- |
| 実装 | 要件どおりに作られていない | **「ゲートを通ればOK」の検証**。多ければ、どのゲートで止められたはずかを rule-log に記録し、ゲートを強くする |
| 設計 | 設計書の決定が誤っている・足りない | **設計工程からの流出**。設計の指摘密度が範囲内でも、流出が多い機能群はレビューが効いていなかったと判断する |
| 転記 | 設計書は正しいが、転記が誤っている | 型の品質。標準化チームへ |
| ハーネス | Lint・hooks・CI・ツールの誤り | 型の品質。標準化チームへ |

**判断すること**

- **結合を終えてよいか**: 従来の完了基準（バグの収束・密度が範囲内）に加えて、引き渡しの消化率 100%。
- **ゲートを直すか**: 実装起因の不具合ごとに判断する。早く直すほど、後に続く機能に効く。
- **設計の評価を見直すか**: 設計起因の不具合が多い機能群は、設計工程の評価を見直す。

**テストケースの作り方が変わるとき**

目指すのは、RDRA の構造化データや [himotoki](https://github.com/mstkfeb20-collab/codegraph)（要求からソースコードへの影響分析）の構造化データからテストケースを作ること。

- **独立性**: 実装は RDRA → ED → ID 設計 → 要件 → コードの経路で、テストは RDRA から直接作る。**根拠の経路が別**なので、人を分けなくても独立性を保てる。RDRA そのものの誤りは実装とテストの両方に入るが、これは従来の要件誤りと同じで、受入やお客様のレビューで拾う。
- **試験密度はモデルの網羅率に置き換える**: 生成するなら件数はいくらでも増やせる。RDRA の業務フロー・ユースケース・状態遷移・条件のバリエーションのうち、テストケースが1件以上あるものの割合で見る。
- **回帰の範囲は himotoki で決める**: 変更した要件から影響するコードと機能を引き、回帰させるテストを機械的に選ぶ。結合テストが実際にどの要件・コードを通ったか（到達率）も測れる。
- **人が見るのはテストケースではなく生成のルール**: 試験リーダーは観点の展開のルールと網羅率の結果を見る。③ で人がテストではなくゲートを管理するのと同じ構造。
- **当面**: パイロットでは人がテストを作って従来の指標で測る。生成に切り替えたら、試験密度をモデルの網羅率に置き換える。

## 運用の注意

- `ID設計.xlsx`（機能一覧）は git でマージできない。課題の決定で機能一覧が変わる PR は、同時に複数を出さず、1本ずつ順に通す。
- 指標の基準値（設計の行数あたり・KLOC の比率・ゲートの基準値）は、パイロットで作り、品質計画に書く。
