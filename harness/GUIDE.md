# ハーネス運用ガイド

tazuna を使った開発で、人が知っておくべきことをまとめる。エージェント向けの指示は `AGENTS.md` と `.github/skills/` にある。

## ルールは破れない場所から守る

エージェントに守らせたいことは、上の層で防げないかを先に考える。文章で伝えるのは最後の手段。

| 優先 | 層 | 防ぎ方 | このリポジトリでの例 |
| --- | --- | --- | --- |
| 1 | 設計 | 間違えようのない型・API・境界にする | `Money` 型、`Reservation` の遷移メソッド |
| 2 | Lint・型・テスト | 成果物の違反を機械的に検出する | `scripts/lint/`、`ArchitectureTest` |
| 3 | 実行検証 | 動かして結果を証拠として残す | `mvn verify`、PRの証拠欄 |
| 4 | 文章 | 判断基準を skills・docs で伝える | `.github/skills/`、`docs/` |

これとは別に、エージェントの**行為**は hooks で止める。

| | Lint | hooks |
| --- | --- | --- |
| 見るもの | 成果物（コード・文書） | 行為（コマンド・ファイル編集） |
| 効く相手 | 人もエージェントも | エージェントだけ（作業中） |
| 向いているもの | コードに痕跡が残る違反。業務の不変条件は必ずこちら | 取り返しがつかない操作、痕跡が残らない操作、保護ファイルの編集 |
| 置き場所 | `scripts/lint/` | `.github/hooks/` |

hooks は呼び出し役にもなる（編集のたびに `run-all.sh --fast` を実行）。判定ロジックは Lint にだけ書き、hooks に重複させない。

## 置き場所の判断基準

| 書きたいもの | 置き場所 | 管理者 |
| --- | --- | --- |
| 常に守る原則・基本コマンド・参照先 | `AGENTS.md`（60行以内） | 案件リーダー |
| 調査・設計・レビューの進め方 | `.github/skills/` | base: 標準化チーム／proj: 案件リーダー |
| 業務の決定（設計） | `docs/design/` の設計書（要件・テスト仕様・作業一覧は、ここから転記ツールが作る。[設計書と転記先](design-and-transcription.md)） | 社員 |
| 完了条件 | `docs/requirements/`（設計書から転記。手で直さない） | 社員 |
| 業務ルール・用語・機能一覧 | `docs/domain/` | 社員 |
| レイヤー・依存方向・作法 | `docs/architecture.md`、`docs/conventions.md` | 案件リーダー |
| 機械的に判定できるルール | `scripts/lint/common/`（型）、`scripts/lint/domain/`（案件） | 標準化チーム／社員 |
| 危険な操作・保護ファイル | `.github/hooks/deny-commands.txt`、`protected-paths.txt` | 標準化チーム |

## skillsの命名

- `base-*`：どの案件でも使う進め方。標準化チームが作り、案件では変更しない。
- `proj-*`：ドメイン特有の進め方。協力会社・社員が作り、案件リーダーが承認する。
- proj は base と同じことをしない。base を前提にするときは本文で参照する。
- 業務ルールはスキルに直接書かず、`docs/domain/` を参照させる。

## 開発の流れ

1. 社員が設計書を書いてレビューし、転記ツールで要件・テスト仕様・作業一覧を作る（何を書き、どう渡るかは [設計書と転記先](design-and-transcription.md)）。issue には要件IDを書く。
2. エージェントが `base-task-workflow` に沿って実装する。作業中は hooks が危険な操作を止め、編集のたびに Lint が走る。
3. エージェントが Lint・テストを通し、PRに実行結果と証拠を書いて提出する。
4. CI が Lint・hooks の自己テスト・`mvn verify` を再実行する。
5. CODEOWNERS で割り当てられた人が、業務上の正しさと証拠を見て承認する。

## ミスが起きたとき

1. 指摘した人が `harness/rule-log.md` に1行記録する。
2. `base-harness-improvement` の順（設計 → Lint → 実行検証 → 文章）で防ぐ層を決める。
3. 取り返しがつかない操作は、順番に関係なく hooks で止める。

## 月次の見直し

案件リーダーが月に1回行い、`harness/metrics.md` を更新して標準化チームに共有する。

- 同じ違反が2回以上あれば、より上の層で防げないか検討する。
- `docs/domain/invariants.md` で「文章」のままの条件を、上の層に移せないか検討する。
- 半年発火していない Lint や、使われていない docs は削除を検討する。
- 古くなったコードの書き方が残っていれば、先に Lint で新しい発生を止めてから既存箇所を直す。
- `AGENTS.md` が肥大化していれば、詳細を docs・skills へ移す。
- 他の案件でも使えそうな `proj-*` や `lint/domain` は、型への昇格候補として標準化チームに提案する。
