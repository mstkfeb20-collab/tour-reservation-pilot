# 設計書と転記先：何を書き、どう渡るか

tazuna では、人が書くのは設計書（`docs/design/`）だけで、エージェントが読む要件・テスト仕様・作業一覧は、設計書から転記ツール（`scripts/design/transcribe.py`）が作る。このページは、二つの違いと、1行が設計書からどこへ移るかを、パイロット（ツアー予約の「予約取消」）の実物で示す。

## 二つに分けている理由

- **設計書は「考える形」。** 検討は業務設計から始まり、業務 → 共通の方式 → データ → 機能・画面 → テストの順に固まる。設計書の種類と見出し（ID 設計の設計項目）は、その順で検討を進め、決定をそれが属する場所に置くための型で、何を決めればよいかのチェックリストも兼ねる。
- **転記先は「使う形」。** 実装に要るのは、機能ごとの横断面（完了条件・テスト仕様・守る条件・作業）。決まったことを渡す形で、何を決めればよいかは教えてくれない。横断面から書き始めると、排他制御・日時・認可・操作ログのように機能をまたぐ決定を機能ごとに決めてしまい、ばらばらに重複する（Lint の ★ はこれを見つける）。
- **正本は設計書だけ。** 転記先は手で直さない（Lint COMMON-008）。直すときは設計書を直して転記し直す。
- **エージェントに設計書を直接読ませない。** 書類の種類ごとに分かれた設計書を、エージェントが書類をまたいで読み合わせると、読むたびに解釈が揺れる。転記がその読み合わせを決まった手順で行う。エージェントが実装の根拠にしてよいのは転記先と DDL、ID で指された設計書の行だけで、それでも設計書を根拠にしたときは PR に「設計書から: 行ID（理由）」と書く（AGENTS.md の原則7）。

## 並べて比べる

| | 設計書（`docs/design/`） | 転記先（`docs/requirements/`・`docs/tasks/` ほか） |
| --- | --- | --- |
| 何のための形 | 決めるため | 作る・確かめるため |
| 分け方 | 書類の種類ごと（方式・画面・処理・テーブル・テスト仕様…）。1ファイル1書類 | 機能ごと（処理設計書の名前のファイル）。共通の決まりは別のファイル |
| 並び | 設計項目（見出し）の順 | 使い方の順（完了条件・テスト仕様・実装するときの条件・型・Lint で守る決まり・作業） |
| 1行 | `- [番号] 本文`（決定1つ） | `- 本文（行ID・設計項目名）`。本文は同じで、出どころが付く |
| 書く人 | 社員（業務の決定）。AI の補助を使ってよい | 誰も書かない。転記ツールが作る |
| 直し方 | PR でレビューして直す | 直さない。設計書を直して転記し直す |
| 主な読み手 | 社員・レビューする人・顧客 | エージェント・テストを作る人・PR をレビューする人 |
| 決めないこと | 「該当なし（理由）」と書く | 行が出ない |
| 図・表 | 説明する行の直下に字下げして書く | 行と一緒に移る |

## 設計書に書くこと・書かないこと

書くこと

- 決定事項を、その決定が属する書類の見出しの下に1行ずつ。値・条件・順序・例外・計算・メッセージ・権限・状態の移り方など。
- 機能をまたぐ決定（排他制御・日時の扱い・認可・操作ログなど）は共通の書類に。機能の書類には、共通と違うところだけを書く。
- 書かないと決めた必須の見出しには「該当なし（理由）」。

書かないこと

- 決まっていないことの推測。決まるまで空けておき、質問として残す（issue にする）。

**空と「該当なし」は意味が違う。** 必須の見出しに「該当なし（理由）」と書くのは、「書くことはない」と決めた決定。何も書いていない必須の見出しは**未決**で、転記すると要件ファイルの「未決」に載り、エージェントはその部分を実装しない（PR に「未対応: 行ID（未決）」と書く）。決まったら設計書に書いて転記し直す。
- ほかの書類で決めたことの写し。必要なら行IDで指す（例「S-22-001/D-06003/1 と同じ」）。
- 転記先の形（「完了条件:」「作業:」など）。どこへ移るかは見出しの設計項目で決まり、書く人は選ばない。

## 1行はどこへ移るか

行の移り先は、見出しの設計項目の属性（性質・機械検査・業務承認）と、書類が機能のものか共通のものかで決まる（`ID設計.xlsx` の振り分け表）。例外の行だけ、行末に `{性質:振る舞い 機械検査:実行で可}` のように書いて上書きできる。

| どんな行か | 移り先 | 設計書の行 → 転記先での表れ方（パイロットの実物） |
| --- | --- | --- |
| 機能の振る舞いで、業務の承認が要る | 要件ファイルの `## REQ-xxxxx` の「完了条件」 | 処理設計書 S-22-002 の「事前条件」に `- [2] 出発日の前日までであること` → `docs/requirements/S-22-002_予約取消.md` の REQ-22002 に `出発日の前日までであること（S-22-002/D-01004/2・事前条件）` |
| テスト仕様書の行 | 同じ要件ファイルの「テスト仕様」 | S-26-002 の「境界値・同値クラス」に `- [2] 取消料の1円未満の切り捨て` → `取消料の1円未満の切り捨て（S-26-002/D-15003/2・境界値・同値クラス）`。テストに `@Tag("S-26-002/D-15003/2")` を付ける |
| エージェントへの条件（機能） | 要件ファイルの「実装するときの条件」 | S-22-002 の「ロックの順序」 → `RESERVE → TOURINFO → REFUND の順に更新する…（S-22-002/D-06007/1・ロックの順序）` |
| エージェントへの条件（共通） | `docs/conventions.md` | 方式設計書などの、全機能が守る作法 |
| 機械で守る決まりで、業務の承認が要る | 要件ファイルの「型・Lint で守る決まり」と、作業一覧 | S-22-002 の「状態と状態遷移」 → 要件に根拠として載り、作業一覧の「型・API・DB 制約で書けなくする」に `- [ ] 振込状況は 0 未振込 → 9 取消…（S-22-002/D-04004/1）` |
| 設計・Lint・実行検証・hooks・業務の承認が要らないテスト | `docs/tasks/` の作業一覧（チェックボックス） | 方式設計書 S-11-001 の「SQLの書き方規約」 → `docs/tasks/S-11-001_方式設計書.md` の「Lint を足す」に `- [ ] SQL は文字列連結で組み立てない（S-11-001/D-05016/1）` |
| 共通の振る舞いで、業務の承認が要る | `docs/domain/candidates/`（不変条件の候補） | 社員が承認したものを `invariants.md` に移す |
| 知識（背景・用語の説明など） | `docs/domain/background.md` | — |
| 機能の書類で、必須の見出しが空（未決） | 要件ファイルの「未決」 | テスト仕様書 S-26-002 の「境界値・同値クラス」が空 → `- 未決: 境界値・同値クラス（S-26-002/D-15003）`。エージェントは実装もテストもしない |

作業一覧の節は、防ぐ層の順に「型・API・DB 制約で書けなくする」「Lint を足す」「テストを書く（業務承認の要らない振る舞い）」「動かして測り、PR に結果を添える」「hooks で操作を止める」「承認されているか確かめる」。

## 一つの機能で見ると

予約取消を実装するエージェントに渡るのは、次の3つだけになる。

- `docs/requirements/S-22-002_予約取消.md`：画面設計書 S-21-001・処理設計書 S-22-002・テスト仕様書 S-26-002 から、この機能の完了条件・テスト仕様・実装するときの条件・型・Lint で守る決まりを集めたもの
- `docs/tasks/S-22-002_予約取消.md`：同じ書類から、この機能の作業を集めたもの
- `db/schema/*.sql`：テーブル・列の意味と制約（列の説明が、区分値の意味を決めた設計書の行IDを指す）

設計書では20を超えるファイル（共通の書類を含む）に分かれていた決定が、機能の横断面になって渡る。共通の書類（方式・メッセージ・セキュリティなど）の決定は、`docs/conventions.md` と共通の作業一覧に入り、どの機能でも同じものを読む。

## 直すときの流れ

1. 設計書を直し、書き手がスキル `base-design-review` で点検する（書類をまたいだ食い違い・未定義・抜け）。結果を `docs/review/設計書の点検.tsv` に残し、止める種別がなく、質問が issue になってから、人のレビューを頼む（Lint COMMON-011）。人がレビューしてマージする。点検はレビューではなく、品質の指標は人のレビューの指摘で取る（`harness/metrics.md`）。
2. `python3 scripts/design/transcribe.py` で転記し、転記の PR で要件とテスト仕様を確かめてマージする。設計書を直してから転記するまでのあいだは、進捗に「要転記」と出る。
3. 実装の PR で、エージェントが「設計書から:」を書いていたら、転記先にない行は転記の漏れか設計書の置き場所の誤りの候補。PR レポートに出るので、転記ツール（標準化チーム）か設計書を直す。
